# Настройка

Файл в YAML, путь задаётся флагом `-config`, по умолчанию
`/etc/antibot/config.yaml`. Пример с комментариями лежит в
[deploy/config.example.yaml](../../deploy/config.example.yaml) и
проверяется тестом: если пример разойдётся с кодом, тест упадёт.

Две вещи, заданные с первого дня:

- **Всё имеет умолчания.** Нода обязана работать с пустым файлом.
- **Опечатка в имени поля — ошибка при запуске**, а не молча
  проигнорированное намерение. Человек, написавший `trusted_proxy` вместо
  `trusted_proxies`, узнает об этом сразу, а не при разборе инцидента с
  подделанным адресом.

Проверка идёт **до того, как заняты порты**. Негодная настройка
останавливает запуск, а не роняет уже работающую ноду через секунду после
старта. Занятый порт — тоже отказ запуска, с именем ключа и адресом:
нода, поднявшаяся без одной из своих дверей, выглядит живой, и
недостающую дверь находят, только когда она нужна.

Здесь — настройки **ядра**. У админки, отдельной программы
`antibot-admin`, свои — [admin.yaml](#adminyaml--настройки-админки), и
`config.yaml` она не читает: в нём токен облака.

## listen

```yaml
listen:
  http: ":8080"
  https: ":8443"
  admin: "127.0.0.1:8091"
  control: "/var/lib/antibot/core.sock"
```

| Ключ | Умолчание | Что |
|---|---|---|
| `http` | `:80` | трафик клиентских доменов |
| `https` | `:443` | то же с TLS |
| `admin` | `127.0.0.1:8091` | служебный порт: `/healthz` и `/stats` |
| `control` | `/var/lib/antibot/core.sock` | сокет управления для админки; пусто — сокета нет |

Служебный порт отдельно от 80 и 443 потому, что те отдают трафик
клиентских доменов, и `/healthz` на них превратился бы в страницу,
которой нет, на каждом защищённом сайте. Наружу он не публикуется.

Хотя бы один из `http` и `https` должен быть задан, иначе запуск
останавливается: нода без слушателей ничего не делает.

Имя `listen.admin` досталось от ранней версии и означает **служебный**
порт, а не админку — та отдельная программа со своими настройками.

`listen.control` — unix-сокет, через который админка спрашивает ядро о
том, что живёт только в его памяти: оповещения, связь с облаком,
сертификаты, версия и время запуска; через него же просит перечитать
изменённый файл или перезапуститься. Права `0660`: пользователь ядра и
группа, в которой состоит админка. Ядру с готовыми правилами и без
админки сокет не нужен — пустое значение его выключает. Сокет, оставшийся
от упавшего ядра, при запуске заменяется; сокет, на котором кто-то
отвечает, — отказ запуска: это второе ядро.

## tls

```yaml
tls:
  certificates_dir: "/etc/letsencrypt/live"
  uploaded_dir: "/var/lib/antibot/shared/certificates"
  self_signed_dir: "/var/lib/antibot/certs"
  reload_interval: 30s
```

| Ключ | Умолчание | Что |
|---|---|---|
| `certificates_dir` | пусто | каталог сертификатов, который ведут руками или certbot |
| `uploaded_dir` | `/var/lib/antibot/shared/certificates` | куда ложатся сертификаты, загруженные через админку; пусто — загрузка выключена |
| `self_signed_dir` | `/var/lib/antibot/certs` | где хранить запасной |
| `reload_interval` | `30s` | как часто просматривать каталоги заново |

Каталогов два, а не один, намеренно: `certificates_dir` часто принадлежит
certbot или смонтирован только для чтения, и нода не пишет в каталог,
который ведёт кто-то другой. Просматриваются оба, раскладка одна. Если
сертификат на одно имя есть в обоих, работает тот, что живёт дольше.

Самоподписанный **сохраняется** на диск. Это важнее, чем кажется:
сертификат, создаваемый заново при каждом запуске, меняет отпечаток
сайта на каждый перезапуск.

Подробнее о раскладке каталога — [install.md](install.md).

## upstreams

```yaml
upstreams:
  - host: "shop.example.ru"
    to: "http://127.0.0.1:3000"
  - host: "*.example.ru"
    to: "http://127.0.0.1:3001"
  - host: "*"
    to: "http://backend:80"
```

Три формы имени, в порядке убывания точности:

| Форма | Что покрывает |
|---|---|
| `shop.example.ru` | точное имя |
| `*.example.ru` | любой поддомен любой глубины, но **не** сам `example.ru` |
| `*` | маршрут по умолчанию |

**Порядок строк ни на что не влияет.** Выбирается сначала точное
совпадение, затем самый длинный подходящий шаблон, и только потом
умолчание. Правило «кто выше, тот и прав» в конфигурации маршрутов ловит
людей десятилетиями, и здесь его нет.

Оговорка про TLS: подстановочный знак в **сертификате** покрывает ровно
одну метку, поэтому для `a.b.example.ru` маршрут по `*.example.ru`
найдётся, а сертификат `*.example.ru` — не подойдёт.

Имена приводятся к одному виду: без порта, в нижнем регистре, в punycode.
`Пример.РФ`, `пример.рф.` и `xn--e1afmkfd.xn--p1ai` — это одно имя, и в
правиле, и в маршруте, и в событии.

Домены можно добавлять и не трогая этот файл — из админки или командой
`antibot domains`; они лежат отдельно, см. [`domains`](#domains). На имя,
известное обоим спискам, побеждает `upstreams`.

## trusted_proxies

```yaml
trusted_proxies:
  - "10.0.0.0/8"
```

Кому разрешено проставлять `X-Forwarded-For`. **Пусто по умолчанию**, и
это единственно возможное умолчание: заголовок ставится одной строкой
curl, и доверие к нему по умолчанию означает, что любой желающий
назовётся кем угодно — а значит, обойдёт любое правило по адресу и
подставит под запрет чужую сеть.

Цепочка читается справа налево: справа тот, кто ближе, и каждый следующий
добавлен предыдущим. Идём, пока адреса доверенные; первый недоверенный и
есть клиент. Всё, что левее, написал он сам. Мусор в цепочке означает
«дальше не верим»: разобрать, кто его вписал, уже невозможно.

## own_networks

```yaml
own_networks:
  - "203.0.113.7/32"
```

Свои адреса: мониторинг, VPN, рабочая машина. Проверяются **раньше
правил** и всегда пропускаются; в событии помечаются `rule: "own network"`.

Отдельный слой, а не правило с высоким приоритетом. Своя сеть, вписанная
исключением в десять правил, однажды окажется забытой в одиннадцатом — и
собственный мониторинг попадёт под запрет ровно тогда, когда он нужен.

## node_id_file

```yaml
node_id_file: "/var/lib/antibot/node.id"
```

Идентификатор установки. Нода создаёт его сама при первом запуске —
шестнадцать случайных байт, — и хранит на диске: пересоздаваемый при
каждом запуске идентификатор превращал бы одну установку в новую на
каждый перезапуск.

Он **не выводится** из домена, адреса или железа. Облаку нужно только
отличать установки друг от друга, а не узнавать их.

## events

```yaml
events:
  dir: "/var/lib/antibot/events"
  max_size: 268435456
  keep_days: 14
  queue: 4096
```

| Ключ | Умолчание | Что |
|---|---|---|
| `dir` | `/var/lib/antibot/events` | куда писать |
| `max_size` | 256 МиБ | предел файла, после которого начинается следующий |
| `keep_days` | 14 | сколько суток хранить; **0 означает «не удалять»** |
| `queue` | 4096 | сколько событий помещается в буфер до записи |

`keep_days: 0` — осознанно опасное значение: диск кончится молча.

При переполнении очереди событие теряется, но запрос **не ждёт диска**.
Журнал существует ради разбора постфактум, а сайт — ради посетителей.
Счётчик потерь виден на служебном порту, в `/stats`: молча теряющий
журнал хуже отсутствующего, потому что по нему делают выводы.

Формат событий — [operations.md](operations.md).

## admin_ui

Секции больше нет: админка — отдельная программа со своими настройками,
[admin.yaml](#adminyaml--настройки-админки). Если она осталась в
`config.yaml` от прежней версии, ядро не запустится и скажет, куда её
перенести, — молча проигнорированная, она оставила бы владельца гадать,
почему админки нет.

## Общий каталог

Что пишет админка — правила, домены, команда оповещений, загруженные
сертификаты сайтов, — по умолчанию лежит в `/var/lib/antibot/shared`.
Админка работает под другим пользователем, а атомарная замена файла
требует права записи в его каталог. Выдать это право на весь
`/var/lib/antibot` значило бы дать админке подменить токен облака и
идентификатор ноды. Поэтому запись разрешена группе только в `shared`,
остальной каталог ей только для чтения — ради событий и сокета.

Установка до разделения держала эти файлы прямо в `/var/lib/antibot`.
Работает она и так: пути заданы в её `config.yaml`. Переносить их в
`shared` нужно, когда ставится `antibot-admin`, — [install.md](install.md).

## rules

```yaml
rules:
  file: "/var/lib/antibot/shared/rules.json"
  reload_interval: 5s
```

Файл перечитывается на лету: изменение замечается по времени и размеру.
Проверка дешёвая — одно обращение к метаданным файла. Правку из админки
ядро берёт сразу: админка просит его перечитать файл через сокет.

Битое правило отбрасывает **весь** набор, а прежний остаётся в силе.
Набор, применённый наполовину, выглядит работающим и потому опаснее
отказа.

## domains

```yaml
domains:
  file: "/var/lib/antibot/shared/domains.json"
  reload_interval: 5s
```

Домены, добавленные во время работы: из админки или командой

```bash
antibot domains add shop.example.ru http://127.0.0.1:8080
antibot domains list
antibot domains remove shop.example.ru
```

YAML нода не пишет, поэтому домены — отдельный файл по образцу
`rules.json`: та же проверка, та же атомарная замена, то же перечитывание
на лету. Работают оба списка вместе, и на имя, известное обоим,
**побеждает `upstreams`** — написанное руками владельцем машины не
перебивается из админки. Маршрут по умолчанию `*` — только в
`upstreams`.

Битый файл при запуске — ошибка; битый на лету — прежний список остаётся
в силе, и ни один добавленный сайт не пропадает из-за опечатки.

## facts

```yaml
facts:
  enabled: true
  dir: "/var/lib/antibot/facts"
  # url: "https://updates.example.com/facts"
  interval: 24h
```

Базы сетей и отпечатков. `enabled: false` выключает их применение
целиком — та самая строка, которая обещана в протоколе.

Без `url` нода базы не загружает; применить набор с диска можно всегда:
`antibot facts apply`. Подробнее — [facts.md](facts.md).

Загрузка идёт раз в сутки плюс разброс. Токен один на оба направления, и
анонимной раздачи баз нет — но брать его из этого файла необязательно:
нода получает токен сама, когда владелец отмечает «получать обновления
безопасности» в админке ([cloud.md](cloud.md)). Заданный здесь `url`
главнее того, что пришлёт облако.

## cloud

```yaml
cloud:
  token: ""
  # url: "https://updates.example.com/ingest"
  interval: 15m
  state_dir: "/var/lib/antibot/aggregate"
  link_file: "/var/lib/antibot/cloud.json"
  # register_url: "https://updates.netbota.ru"
```

Отправка обезличенных агрегатов. **Пустой токен — отправки нет вовсе.**
Не «выключена настройкой», а не имеет адресата: без токена нода не знает,
куда слать, и не пытается.

Что именно уходит и что не уходит никогда — [protocol/aggregate.md](protocol/aggregate.md).

`interval` — как часто закрытые окна собираются в пачку и отправляются;
само окно всегда пять минут. Первая пачка уходит через случайную долю
интервала после запуска: установки из одного образа иначе стучались бы в
облако в одну и ту же секунду.

`state_dir` — открытое окно и пачки, которые облако ещё не приняло: не
больше 200 штук, около двух суток. Создаётся только при заданном токене.
Что там лежит и что уйдёт следующим, показывают `antibot aggregate
status` и `antibot aggregate show`.

`link_file` — что владелец ответил в админке про облако и токен, если он
его взял. Это **состояние ноды, а не настройки**: единственный файл,
который админка тут пишет, права `600`. Заданный здесь `token` главнее
всего, что в нём лежит. Пустой `link_file` означает, что взять токен из
админки нельзя вовсе — остаётся только написать его в этот файл рукой.

`register_url` — куда нода просится за токеном. Пусто — адрес рядом с
`url`, а если и его нет, тот, с которым собран бинарник. Подробно —
[cloud.md](cloud.md) и [protocol/registration.md](protocol/registration.md).

## alerts

```yaml
alerts:
  enabled: true
  command: ""
  file: "/var/lib/antibot/shared/alerts.json"
  timeout: 30s
  window: 5m
  site_error_share: 0.5
  site_min_requests: 20
  spike_factor: 5
  spike_min_requests: 500
  spike_min_blocked: 200
  rule_min_matches: 50
  cert_days: 14
  disk_min_mb: 1024
  facts_max_age: 168h
  outbox_max: 12
```

| Ключ | Умолчание | Что |
|---|---|---|
| `enabled` | `true` | считать ли триггеры вовсе |
| `command` | пусто | команда доставки, через `sh -c`; задана здесь — побеждает заданную в админке |
| `file` | `/var/lib/antibot/shared/alerts.json` | куда админка кладёт свою команду; пусто — команда только из конфигурации |
| `timeout` | `30s` | сколько ждать команду, от `1s` до `5m` |
| `window` | `5m` | окно, на которое смотрит каждый триггер трафика; целые минуты, от `1m` до `1h` |
| `site_error_share` | `0.5` | доля 5xx сайта, при которой он «не отвечает» |
| `site_min_requests` | `20` | меньше запросов до сайта за окно — не судить |
| `spike_factor` | `5` | во сколько раз больше обычного — всплеск; не меньше `1.5` |
| `spike_min_requests` | `500` | меньше запросов за окно — не всплеск, как бы ни было мало обычно |
| `spike_min_blocked` | `200` | то же для отрезанных |
| `rule_min_matches` | `50` | то же для одного правила; у нового правила решает только он |
| `cert_days` | `14` | за сколько дней до конца срока говорить о сертификате; `0` — не говорить |
| `disk_min_mb` | `1024` | сколько свободного места под журналом считать концом; `0` — не смотреть |
| `facts_max_age` | `168h` | сколько набор фактов может не обновляться, если нода их загружает |
| `outbox_max` | `12` | сколько неотправленных пачек агрегатов — уже поломка; `0` — не смотреть |

Пороги по умолчанию рассчитаны на то, чтобы маленький сайт не получал
тревог от десятка ботов, а большой — не тонул в них. «Обычное» — среднее
за час до окна; первые полчаса после запуска всплесков нет. Как приходит
сообщение, что получает команда и готовые шаблоны — [alerts.md](alerts.md).

## Что проверяется при запуске

- задан хотя бы один слушатель;
- `trusted_proxies` и `own_networks` — сети вида `10.0.0.0/8`, а не
  адреса;
- у каждого `upstreams` заполнены `host` и `to`;
- секция `admin_ui` — ошибка с подсказкой, куда её перенести;
- `cloud.token` без `cloud.url` — ошибка: слать некуда;
- `cloud.token` без `cloud.state_dir` — ошибка: негде держать неотправленное;
- `facts.url` без `facts.dir` — ошибка: класть некуда;
- `facts.url` без `cloud.token` **и** без `cloud.link_file` — ошибка:
  токен взять неоткуда и положить некуда;
- пороги `alerts` в своих границах: окно — целые минуты от `1m` до `1h`,
  доля — больше нуля и не больше единицы, `spike_factor` — не меньше `1.5`;
- длительности имеют вид `30s`, `15m`, `24h` и не отрицательны.

Свой тип длительности нужен потому, что YAML разобрал бы `30` как
тридцать наносекунд. Это хуже, чем ошибка разбора: интервал в тридцать
наносекунд не сломает запуск, он просто сожжёт процессор в бою.

## admin.yaml — настройки админки

Файл `antibot-admin`, по умолчанию `/etc/antibot/admin.yaml`, путь — флагом
`-config`. Пример с комментариями — [deploy/admin.example.yaml](../../deploy/admin.example.yaml),
тоже под тестом. Опечатка в имени поля — ошибка, как в `config.yaml`.

```yaml
listen: "127.0.0.1:8090"
# certificate: "/etc/letsencrypt/live/admin.example.ru/fullchain.pem"
# key: "/etc/letsencrypt/live/admin.example.ru/privkey.pem"
# redirect_from: ":8089"
uploaded_dir: "/var/lib/antibot-admin/admin-ui"
users_file: "/var/lib/antibot-admin/admin.json"
tokens_file: "/var/lib/antibot-admin/api-tokens.json"
session_ttl: 12h
language: en

core:
  socket: "/var/lib/antibot/core.sock"
  events_dir: "/var/lib/antibot/events"
  rules_file: "/var/lib/antibot/shared/rules.json"
  domains_file: "/var/lib/antibot/shared/domains.json"
  certificates_dir: "/var/lib/antibot/shared/certificates"
  alerts_file: "/var/lib/antibot/shared/alerts.json"
```

| Ключ | Умолчание | Что |
|---|---|---|
| `listen` | `127.0.0.1:8090` | адрес |
| `certificate`, `key` | пусто | задаются **вместе** |
| `redirect_from` | пусто | адрес, где HTTP отвечает кодом 308 |
| `uploaded_dir` | `/var/lib/antibot-admin/admin-ui` | куда ложится пара, добавленная на странице Settings, когда `certificate` и `key` пусты; работает со следующего запуска. Пусто — добавлять нельзя |
| `users_file` | `/var/lib/antibot-admin/admin.json` | учётки |
| `tokens_file` | `/var/lib/antibot-admin/api-tokens.json` | токены [API](api.md), хешами; пусто — API выключен |
| `session_ttl` | `12h` | срок сессии |
| `language` | `en` | язык страниц, когда его не выбрал человек и не назвал браузер: `en` или `ru`; другое — отказ при запуске. См. [Язык](admin.md#язык) |
| `core.socket` | `/var/lib/antibot/core.sock` | `listen.control` ядра |
| `core.events_dir` | `/var/lib/antibot/events` | `events.dir` ядра; только чтение |
| `core.rules_file` | `/var/lib/antibot/shared/rules.json` | `rules.file` ядра |
| `core.domains_file` | `/var/lib/antibot/shared/domains.json` | `domains.file` ядра |
| `core.certificates_dir` | `/var/lib/antibot/shared/certificates` | `tls.uploaded_dir` ядра; пусто — загрузки нет |
| `core.alerts_file` | `/var/lib/antibot/shared/alerts.json` | `alerts.file` ядра; пусто — команду оповещений из админки не поменять |

Пути в `core` — те же, что в `config.yaml` ядра: админка его не читает,
поэтому они названы здесь второй раз.

**Не-loopback адрес без сертификата — отказ при запуске.** Не
предупреждение: пароль уходил бы по сети открытым текстом, а это не
неудобство, а выданный доступ. Хотите открыть админку наружу — сначала
задайте сертификат или добавьте пару на странице Settings. Он
перечитывается на лету, не чаще раза в 30 секунд: продлённый certbot'ом
берётся без перезапуска.

`redirect_from` работает только вместе с сертификатом. Код 308, а не 301:
301 разрешает браузеру сменить метод на GET, и отправленная форма входа
тихо превратилась бы в пустой запрос.

Учётки — отдельный файл, а не эти настройки: настройки часто
монтируются только для чтения, а пароль меняют без перезапуска. Без
единой учётки админка не запускается; ядро от этого не зависит.

Токены API лежат рядом по той же причине. API живёт на адресе админки,
под `/api/v1/`, и без неё не поднимается; выпуск, права и ответы —
[api.md](api.md).

При запуске проверяется: `listen` задан, `certificate` и `key` заданы
вместе, `core.socket` и `core.events_dir` не пусты, есть хотя бы одна
учётка, не-loopback адрес — только с сертификатом.
