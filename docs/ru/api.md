# API

Те же числа, что показывает админка, — для программы: мониторинга, своей
панели, CI, который выкатывает правила вместе с сайтом. API живёт на
адресе админки, под `/api/v1/`, и подчиняется её правилам: по умолчанию
loopback, наружу — только с сертификатом. Второго слушателя со своими
правилами нет.

Программа приходит с токеном, а не с сессией. Формы админки токен не
принимают, API не принимает куку сессии: ни одна дверь не открывает
другую, а запросу без куки CSRF нечего подделывать.

## Токены

```bash
antibot api-token issue monitoring                # только чтение, 90 дней
antibot api-token issue ci -scope write -days 30
antibot api-token list
antibot api-token revoke monitoring
```

В stdout команда печатает одно значение — `TOKEN=$(antibot api-token
issue monitoring)` берёт ровно его, слова уходят в stderr. То же умеет
страница «API tokens» админки; там выпуск требует пароль ещё раз, потому
что токен живёт месяцами дольше сессии ([admin.md](admin.md)).

- **Права**: `read` — сводка, события, правила и прогон черновика по
  истории, который ничего не пишет; `write` — ещё и менять правила. Токен
  мониторинга должен только читать: он не должен уметь выключить защиту.
- **Срок** — от 1 до 365 дней, по умолчанию 90. Бессрочного нет: «пока»
  у бессрочного токена длится годами.
- **Хранится хешем** — SHA-256 в `admin_ui.tokens_file`, права `0600`.
  Значение показывается один раз, при выпуске; украденная копия файла
  доступа не даёт. SHA-256, а не PBKDF2, как у паролей: токен — 256
  случайных бит, и замедлять перебор того, что не перебирается, значит
  замедлять каждый запрос.
- **Файл перечитывается на лету**: выпущенный командой токен работает
  без перезапуска ноды, отозванный перестаёт со следующего запроса.
- **Последнее использование** пишется с точностью до десяти минут: иначе
  мониторинг переписывал бы файл несколько раз в секунду.
- **Имя** — буквы, цифры, точка, дефис и подчёркивание, до 64 знаков; у
  живых токенов оно не повторяется: по имени журнал ноды называет, кто
  что поменял. Отозванные и истёкшие остаются в списке — «каким токеном
  ходил CI до 12-го» должно иметь ответ.
- Значение начинается с `abn_` — токен API ноды отличается от токена
  подписки облака с первого взгляда: в конфиге, в журнале, в утёкшей
  вставке.

**Токен — владельца.** Он выпускается только на ноде и никогда не уходит
в облако: у ноды нет кода, который бы его отправлял, облако такие токены
не принимает и не хранит. Токен с правом записи в руках облака значил бы,
что облако может включить правило на чужом сайте, — ровно то, чего оно не
может никогда.

## Запрос

```bash
curl -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8090/api/v1/summary?period=24h'
```

С сертификатом у админки — `https://` и её внешний адрес. Ответы — JSON в
UTF-8, ошибка — `{"error": "…"}` с причиной словами.

| Код | Что |
|---|---|
| `200`, `201`, `204` | ответ; `201` — правило добавлено, `204` — удалено, тела нет |
| `400` | параметр не прочитан. Умолчание молча не подставляется: программа должна узнать, что спросила не то, что получила |
| `401` | токена нет, он неизвестен, отозван или истёк; с заголовком `WWW-Authenticate` |
| `403` | токен только для чтения |
| `404` | такого адреса в API нет, или нет такого правила |
| `409` | правило с таким `id` уже есть |
| `413` | тело больше мегабайта |
| `429` | с этого адреса слишком много отвергнутых токенов — двадцать за пять минут |
| `500` | журнал событий не прочитан; причина — в ответе и в журнале ноды |
| `503` | нода не прочитала файл токенов |

Считаются только отказы: работающий токен в предел не упирается, как бы
часто мониторинг ни спрашивал.

## Сводка — `GET /api/v1/summary`

То, что показывает обзор админки, — тот же код сборки, поэтому числа не
расходятся.

| Параметр | Умолчание | Что |
|---|---|---|
| `period` | `24h` | за какой срок, до `2160h` — 90 дней |
| `top` | `10` | строк в каждом разрезе, до 1000 |

```json
{
  "from": "2026-09-12T12:00:00Z",
  "to": "2026-09-13T12:00:00Z",
  "summary": {
    "events": 18422,
    "ip_count": 3120,
    "decisions": {"pass": 17890, "block": 532},
    "answers": [16010, 402, 1320, 158, 532, 0],
    "latency": {"count": 17890, "p50": 41000000, "p95": 380000000, "p99": 910000000},
    "rules": [{"value": "block-hosting", "count": 532, "ips": 61}],
    "unknown": {"no_net_class": 9120, "no_family": 4410, "self_declared_crawlers": []},
    "…": "…"
  }
}
```

- `decisions` — сколько запросов получило каждое решение;
- `answers` — шесть чисел по классам ответа, по порядку: 2xx, 3xx, 4xx и
  5xx сайта, `blocked` — не пропустила нода, `none` — без кода;
- `latency` — время ответа сайта в **наносекундах**, только по запросам,
  дошедшим до сайта;
- разрезы `rules`, `shadows`, `hosts`, `ips`, `ja4`, `ua`, `paths`,
  `statuses`, `server_error_paths`, `client_error_paths` — строки
  `{value, count, ips}`: значение, запросы и со скольких адресов;
- `unknown` — чего нода не знает: запросы без класса сети, безымянные
  отпечатки, назвавшиеся роботами — у каждого сколько пришло из сети
  роботов (`verified`);
- `series` — ряд по времени, у каждой точки те же шесть классов;
- `truncated: true` — хотя бы один разрез упёрся в предел ключей, и его
  числа неполные.

## События — `GET /api/v1/events`

Новые сверху. Фильтры те же, что на странице событий, и складываются по
«и».

| Параметр | Что |
|---|---|
| `host`, `ip`, `ja4`, `decision` | точное совпадение |
| `rule` | правило, решившее запрос, или сработавшее в тени |
| `status` | код (`404`) или класс (`5xx`, `blocked`) — как на обзоре |
| `q` | подстрока `User-Agent` или пути |
| `limit` | сколько событий, от 1 до 1000, по умолчанию 100 |
| `before` | только старше этого момента — так идут страницы |

```json
{
  "events": [
    {"t": "2026-09-13T11:58:02.123456789Z", "ip": "198.51.100.9", "host": "shop.example.ru",
     "method": "GET", "path": "/api", "proto": "HTTP/2.0", "ua": "curl/8.4",
     "ua_ok": true, "decision": "block", "rule": "block-curl", "status": 403}
  ],
  "next_before": "2026-09-13T11:58:02.123456789Z"
}
```

Событие — ровно строка журнала, как в NDJSON
([operations.md](operations.md)); `dur` — наносекунды.

**Страницы.** Полная страница несёт `next_before` — момент самого старого
события в ней; следующая запрашивается с `before=` этим значением. На
последней странице `next_before` нет. Два события, записанные в одну и ту
же наносекунду по разные стороны границы страницы, могут разминуться —
цена курсора, который не держит на ноде никакого состояния.

## Правила — `GET /api/v1/rules`

В порядке применения, выключенные — после включённых. У каждого — сколько
раз оно сработало за `period` (по умолчанию `24h`) и со скольких адресов;
в тени тоже. Это страница правил админки, и код у них общий.

```json
{
  "from": "2026-09-12T12:00:00Z",
  "to": "2026-09-13T12:00:00Z",
  "events": 18422,
  "rules": [
    {"rule": {"id": "block-hosting", "scope": ["*"], "mode": "active", "priority": 100,
              "condition": {"field": "network.class", "op": "eq", "value": "hosting"},
              "action": {"type": "block"}},
     "matched": 532, "ips": 61, "enabled": true}
  ]
}
```

`rule` — правило ровно так, как оно лежит в `rules.json` ([rules.md](rules.md)).
Если журнал событий не прочитался, ответ — `500`, а не правила с нулями:
программа прочитала бы нули как «не сработало ни разу».

## Прогон черновика — `POST /api/v1/replay`

То же, что `antibot replay`, для одного правила: черновик прогоняется по
журналу вместе с правилами в силе — черновик с `id` правила в силе встаёт
на его место, — и ответ говорит, кого он задел бы. **Ничего не пишется**,
поэтому хватает токена `read`. Предел частоты у прогона свой: счёт
начинается заново по времени событий, а не продолжает чужой.

```json
{
  "rule": {"id": "block-hosting", "scope": ["*"], "mode": "active", "priority": 100,
           "condition": {"field": "network.class", "op": "eq", "value": "hosting"},
           "action": {"type": "block"}},
  "period": "24h",
  "examples": 5
}
```

`period` — по умолчанию `24h`, до `2160h`; `examples` — сколько событий,
на которых черновик сработал, вернуть для разбора глазами: от 0 до 50, по
умолчанию 5.

```json
{
  "from": "2026-09-12T12:00:00Z",
  "to": "2026-09-13T12:00:00Z",
  "events": 18422,
  "ips": 3120,
  "decisions": {"pass": 17710, "block": 712},
  "divergences": {"pass→block": 180},
  "rule": {"id": "block-hosting", "mode": "active", "action": "block",
           "matched": 712, "ips": 61, "hosts": 2, "uas": 14, "share": 0.0386,
           "samples": []}
}
```

- `divergences` — сколько запросов получили бы не то решение, что
  записано в событии. Ради этого прогон и делают: «скольких живых людей
  отрежет новое правило» узнаётся только так;
- черновик в `shadow` решений не меняет — чтобы увидеть, кого он отрежет,
  прогоняйте его с `"mode": "active"`: прогон всё равно ничего не
  включает;
- `share` больше `0.01` — повод пройти примеры руками: столько трафика
  никогда не бывает одними ботами.

## Запись правил

Токен `write`. Те же методы, что у `antibot rules`: правило проверяется
само и в составе набора, файл перечитывается перед правкой — его могли
менять руками — и заменяется атомарно, изменение действует сразу. Каждое
попадает в журнал ноды с именем токена.

| Запрос | Что |
|---|---|
| `POST /api/v1/rules` | добавить готовое правило; тело — правило, как в `rules.json` |
| `POST /api/v1/rules/{id}/enable` | включить |
| `POST /api/v1/rules/{id}/disable` | выключить |
| `POST /api/v1/rules/{id}/mode` | перевести: тело `{"mode": "active"}` или `{"mode": "shadow"}` |
| `DELETE /api/v1/rules/{id}` | удалить; ответ `204` без тела |

```json
{
  "id": "watch-hosting-without-cookie",
  "scope": ["shop.example.ru"],
  "mode": "shadow",
  "priority": 50,
  "condition": {"all": [
    {"field": "network.class", "op": "eq", "value": "hosting"},
    {"field": "cookie", "op": "eq", "value": false}
  ]},
  "action": {"type": "block"}
}
```

```bash
curl -fsS -H "Authorization: Bearer $TOKEN" --data @watch-hosting.json \
  http://127.0.0.1:8090/api/v1/rules
curl -fsS -H "Authorization: Bearer $TOKEN" --data '{"mode": "active"}' \
  http://127.0.0.1:8090/api/v1/rules/watch-hosting-without-cookie/mode
```

Ответ — правило, каким оно стало в силе: `{"rule": {…}}`, `201` на
добавление и `200` на остальное. Программа видит результат, а не эхо
своего запроса.

Лишнее поле тела — ошибка, как и в `rules.json`: опечатка в имени поля
не должна тихо превращаться в пропущенное намерение. `400` — правило не
разобралось или движок его не принимает: неизвестное поле условия,
оператор не для типа поля, режим, которого нет.

**Сразу в `active`** добавить можно, как и командой, но ответ несёт
`warning`, а журнал ноды — строку уровня `WARN`: правило, не побывавшее в
тени, никто не видел в деле. Путь спокойнее — добавить в `shadow`,
прогнать, посмотреть на срабатывания в тени, перевести.

Одновременные изменения не теряют друг друга: чтение и запись файла
правил идут под одним замком, и два запроса CI подряд оба окажутся в
файле.

```
level=INFO msg="a rule was added through the API"
  rule=watch-hosting-without-cookie mode=shadow token=ci address=127.0.0.1
level=INFO msg="a rule's mode was changed through the API"
  rule=watch-hosting-without-cookie mode=active token=ci address=127.0.0.1
```

Правки правила на месте нет: заменить — удалить и добавить заново.
Редактор, собирающий условие по кусочкам, облаку и программам не нужен —
им нужен путь положить готовое правило под ту же проверку.

## Схемы

Машиночитаемые схемы ответов лежат рядом со схемами протокола:
[api-summary](../schema/api-summary.schema.json),
[api-events](../schema/api-events.schema.json),
[api-rules](../schema/api-rules.schema.json) — там же `change`, ответ на
изменение правила,
[api-replay](../schema/api-replay.schema.json),
[api-error](../schema/api-error.schema.json). Тест
`TestAPIAnswersMatchTheSchemas` сверяет с ними настоящие ответы ноды, так
что схема и код не расходятся. Лишнее поле схема не пропускает.

## Границы

- **тот же адрес и те же правила, что у админки**: loopback по умолчанию,
  наружу — только с сертификатом. Без учёток админка не поднимается, а с
  ней и API; без `admin_ui.tokens_file` API выключен;
- **токен — только в заголовке `Authorization`**. В адресе он осел бы в
  журналах прокси и в истории оболочки;
- **кука сессии в API не действует, токен в формах админки не действует**;
- **менять правила — только токеном `write`**; `read` читает и
  прогоняет черновики, но выключить защиту не может;
- те же заголовки, что у страниц: `Cache-Control: no-store`,
  `X-Robots-Tag: noindex`;
- **API — локальная поверхность ноды**, а не часть обмена с облаком:
  [протокол](protocol/) он не меняет и наружу ничего не отправляет.

## Чего пока нет

- доменов и сертификатов — позже, отдельным правом;
- выгрузки журнала целиком — страницы событий идут по тысяче.
