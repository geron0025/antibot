# Правила

Правило — условие и действие. Условие ссылается на **факты**, а не
перечисляет адреса:

```json
{
  "id": "hosting-without-browser",
  "name": "хостинг без браузерного рукопожатия",
  "scope": ["shop.example.ru"],
  "mode": "shadow",
  "priority": 100,
  "condition": {
    "all": [
      {"field": "network.class", "op": "eq", "value": "hosting"},
      {"field": "ua_matches_ja4", "op": "eq", "value": false}
    ]
  },
  "action": {"type": "block", "status": 403}
}
```

Так правило переживает переезд пула: диапазоны меняют хозяев постоянно, и
список из полусотни префиксов внутри правила устаревает молча — а именно
молча устаревшее правило и начинает однажды резать живых людей.

## Условие

Дерево из `all`, `any`, `not` и сравнений `{field, op, value}`. Узел либо
**составной** (ровно одно из `all`, `any`, `not`), либо **сравнение**.
Смешивать нельзя: узел, у которого заполнено и `all`, и `field`, читается
двумя способами, и однажды прочтётся не тем.

Не выражение со своим синтаксисом — такой формат проверяется схемой, его
надёжнее составляет машина, и в ноде нет ещё одного языка, который
пришлось бы сопровождать и фаззить отдельно.

**Всё, что никогда не совпадёт, — ошибка разбора, а не молчание.**
Неизвестное поле, оператор не для этого типа, `cidr` по строке,
`contains` с пустой строкой — правило не встанет, и нода скажет, где
именно:

```
condition.all[1]: поле "ja44" не существует; доступны: alpn, family, grease, h2, …
```

### Поля

```bash
antibot rules fields
```

| Поле | Тип | Откуда |
|---|---|---|
| `ip` | адрес | настоящий адрес клиента |
| `host` | строка | имя домена, нормализованное |
| `method`, `path`, `proto` | строка | из запроса |
| `ua`, `referer` | строка | из заголовков |
| `ja3`, `ja3_hash`, `ja4` | строка | отпечаток TLS |
| `sni`, `alpn`, `tls` | строка | из рукопожатия |
| `grease` | да/нет | клиент прислал GREASE |
| `h2` | строка | отпечаток HTTP/2 |
| `headers`, `headers_hash` | строка | состав заголовков |
| `family` | строка | **из набора фактов**: chrome, curl, go… |
| `ua_matches_ja4` | да/нет | **из набора фактов** |
| `network.class` | строка | **из набора фактов**: hosting, isp, mobile… |
| `network.owner`, `network.country` | строка | **из набора фактов** |
| `network.protected` | да/нет | **из набора фактов**: «не трогать целиком» |
| `network.age` | число | **из набора фактов**: сколько версий записи |

Помеченные «из набора фактов» пусты, пока набор не применён —
[facts.md](facts.md). Правило, ссылающееся на них, до этого просто не
совпадает.

Исключение — `ua_matches_ja4`: это «да/нет», и пустым оно быть не может.
Умолчание — `true`, «нет оснований считать, что клиент врёт». Иначе
правило вида `ua_matches_ja4 == false` заблокировало бы каждого
посетителя на ноде без баз.

### Операторы

| Тип поля | Операторы |
|---|---|
| строка | `eq`, `ne`, `in`, `not_in`, `contains`, `prefix`, `suffix` |
| адрес | то же плюс `cidr`, `not_cidr` |
| да/нет | `eq`, `ne` |
| число | `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in` |

`cidr` принимает список сетей. Немаскированная сеть работает так, как её
прочитает человек: `203.0.113.7/24` — это `203.0.113.0/24`. Адрес,
который не разобрался, не попадает **ни в одну** сеть: иначе запрос без
адреса прошёл бы по `not_cidr` куда угодно.

Пустая строка — обычное значение, а не «не задано». На ней держится
оговорка «клиент не назвался»: `{"field": "referer", "op": "eq", "value": ""}`.

## Область

`scope` — на каких доменах правило действует: `["*"]`, точные имена или
`"*.example.ru"` (сам домен и все поддомены). Обязателен с первого дня:
нода обслуживает не один сайт, а правило, написанное для одного, на
остальных обычно вредно.

## Режимы

| Режим | Что делает |
|---|---|
| `shadow` | совпадение записывается в событие полем `shadow`, запрос идёт дальше |
| `active` | правило выносит решение, перебор на нём останавливается |

**Новое правило включается только через `shadow`.** Правило-наблюдатель
полезно ровно потому, что его читают: сработавшие тени попадают в событие
и в сводку админки, и по ним видно, кого правило задело бы.

`mode` обязателен. Отсутствие `enabled` означает «включено», и это
безопасно ровно потому, что режим задать обязательно: правило не может
оказаться в `active` по недосмотру.

## Действия

```json
{"type": "block", "status": 403, "body": "Access denied"}
{"type": "allow"}
{"type": "ratelimit", "limit": 60, "window": "1m", "key": "ip"}
```

`allow` обязателен как самостоятельное действие — см. ниже про
исключения.

## Порядок применения

Побеждает **первое сработавшее правило в режиме `active`**, в порядке
убывания приоритета. При равных приоритетах порядок задаёт `id`, а не
место в файле: перестановка строк не должна менять решения, иначе прогон
по истории и горячий путь разойдутся на ровном месте.

Отсюда следует, как делаются исключения: **не** отрицанием внутри каждого
запрета, а разрешающим правилом выше по приоритету.

```json
{"id": "allow-monitoring", "priority": 200, "action": {"type": "allow"},
 "condition": {"field": "ip", "op": "cidr", "value": ["203.0.113.0/24"]}}
```

Исключение, вписанное в десять запретов, однажды окажется забытым в
одиннадцатом — и это не заметит никто, потому что забытое исключение
ничем себя не проявляет.

## Ограничитель частоты

Скользящее окно **в памяти процесса**. Это значит:

- при `N` репликах ноды предел фактически умножается на `N`;
- после перезапуска счёт начинается заново.

Сказано прямо, потому что иначе обнаруживается по чужой жалобе. Общий
счётчик потребовал бы того самого хранилища, без которого нода и
задумана.

Отброшенные запросы в счёт не идут: клиент, перестав частить, выходит
из-под ограничения через окно, а не остаётся под ним, пока шлёт.

`key` — по какому полю считать, по умолчанию `ip`. Годятся только
строковые поля: считать частоту по «да/нет» — это две корзины на весь
трафик. Предел ограничен сверху (`1048576`): предел в миллиард означал бы
не мягкое правило, а съеденную память.

Сработавший `ratelimit`, не превысивший предел, **останавливает перебор**
— запрос проходит с пометкой этого правила. Запрет с меньшим приоритетом
по тем же клиентам в этом случае не применится; это стоило разбора в
прошлом поколении, поэтому сказано вслух.

## Прогон по истории

```bash
antibot replay -for 24h -examples 5
```

Проверяет **тот же самый** матчер, что работает на горячем пути, — не его
SQL-перевод. Поэтому «на истории показало одно, в бою сделало другое»
здесь невозможно в принципе.

Что показывает:

- сколько запросов получило каждое решение;
- **расхождения** с тем, что записано в событиях: `pass→block` — это и
  есть «сколько живых людей срежет новое правило»;
- по каждому правилу: сколько совпало, доля, сколько адресов, доменов и
  разных `User-Agent`;
- примеры поимённо, если попросить `-examples`.

Правило, задевающее больше процента запросов, помечается предупреждением:
столько трафика ботовым не бывает.

Ограничитель частоты в прогоне считает **по времени событий**, а не по
часам машины, иначе числа будут не те, что были в бою.

## Командная строка

```bash
antibot rules list                      # в порядке применения
antibot rules add < rule.json           # с проверкой до записи
antibot rules enable ID
antibot rules disable ID                # выключить, не удаляя
antibot rules remove ID
antibot rules check                     # проверить файл, ничего не меняя
antibot rules fields                    # поля и операторы
```

Файл заменяется целиком и атомарно; нода замечает изменение и
перечитывает набор без перезапуска. **Битое правило отбрасывает весь
набор**, а прежний остаётся в силе.

Правила меняются только так — командой. Единственное исключение —
кнопка «включить/выключить» в админке, и она идёт **через ту же запись и
ту же проверку**: у файла правил нет второго писателя.

Возможности включить правило извне нет и не будет.
